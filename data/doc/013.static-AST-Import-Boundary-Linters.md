### Architectural Mandate & Threat Model

In a deterministically sealed simulation architecture, the simulation engine operates strictly as a pure mathematical and legislative reducer. The engine’s purpose is to calculate state transformations, verify physical anatomical limits, and evaluate epistemic visibility without external dependencies. Downstream workflows and generative systems frequently introduce convenience libraries into core simulation units—such as importing animation tools for coordinate math, native filesystem modules for logging, or cloud provider bindings for database access.

Unchecked imports introduce native operating system threads, child processes, ambient clocks, and network sockets into what must remain an isolated state machine. This breaks simulation determinism, inflates isolate bundle sizes beyond edge memory ceilings, and destroys the engine's portability across command-line interfaces, edge isolates, and test environments. Static Abstract Syntax Tree (AST) import boundary linting establishes a static gate that inspects source trees before any build or test phases. Any detected platform I/O, graphics rendering, or unapproved cross-package dependency immediately triggers a non-zero exit code, terminating execution at compile time before compute resources are consumed.

### The Three Legislative Firewall Invariants

The AST analysis engine evaluates the dependency graph using three distinct rules:

- **The Pure Engine Zero-IO Boundary:** Core simulation units must maintain zero platform coupling. The AST inspector rejects any import originating within the simulation core that targets application shells, cloud edge bindings, or native execution runtimes. File system operations, socket networking, transport layer security, child process spawning, and native database bindings are physically prohibited from being imported.
- **The Presentation and Media Quarantine:** The simulation engine remains strictly visual-agnostic. It governs abstract semantics and spatial topologies without awareness of pixels, frames, or audio tracks. The AST boundary automatically fails if any core package attempts to ingest animation frameworks, video composition engines, rendering pipelines, browser automation tools, or graphics canvas packages.
- **The Public Client Ingress Law:** Cross-package module ingestion must pass exclusively through designated, immutable public client boundaries. Direct internal imports into private unit directories, nested submodules, or unexposed helpers of sibling packages are rejected. Upstream consumers are permitted to ingest only validated contracts and projection snapshots exposed through top-level public client barrel files.

### Operational Mechanics: Static AST Analysis vs. Runtime Gating

AST boundary enforcement differs fundamentally from traditional linting or runtime type validation:

- **Pre-Compilation Abstract Syntax Tree Traversal:** The boundary analyzer resolves imports by parsing TypeScript source code directly into AST nodes without compiling or executing the files. By tracking relative paths, ambient node module specifiers, and package aliases, the scanner constructs a directed dependency graph of the entire monorepo.
- **Evaluation at Zero Cost:** Runtime assertions consume memory and execution cycles during simulation ticks, and schema failures inside running isolates incur logging overhead and worker invocations. AST boundary linters operate strictly at the compile-time baseline, halting pull requests and local builds with zero cloud cost and zero compute allocation.
- **Enforcement of Unidirectional Dependency Flow:** In accordance with the system's structural hierarchy, canonical types and law sit at the base, the stateless simulation kernel consumes those types, the runtime ledger records mutations, and presentation spokes depict the resulting output. The AST gate enforces this directionality; higher-level presentation packages or application wrappers may depend downward on schemas, but pure engines cannot reach upward or sideways into execution environments.

### The Negative-Control Adversarial Testing Law

An architectural invariant rule that has not been proven to fail against illegal syntax cannot be certified. To verify that the AST linter acts as an active constraint rather than a passive configuration, the verification harness uses negative-control testing:

- **Synthetic Violation Ingestion:** Automated test fixtures intentionally write temporary, illegal import statements into core engine units.
- **Assertion of Immediate Failure:** The test harness invokes the AST analyzer across the dirty fixture and asserts that the process terminates with an exit status of one, specifically catching the expected rule violation name.
- **Hygiene Restoration:** Once the failure mode is verified, the fixture is unlinked and deleted, ensuring that test artifacts never leak into version control. A test passes only when the clean baseline produces zero infractions and every illegal fixture is caught and rejected.

### Monorepo Integration & Terminal Harness Ingress

The boundary firewall integrates into both automated continuous integration pipelines and local developer cockpits:

- **Manifest Verification Chains:** The root monorepo manifest ties the AST boundary command directly into the primary verification suite. The script runs alongside strict composite type checking, zero-runtime dependency checks, and character encoding scans, blocking any merge that violates structural rules.
- **Terminal Interface Switchboard Hooks:** For local workstation development, the AST boundary check is registered into the curses-based terminal cockpit. Operators can trigger boundary audits via keyboard shortcuts or interactive menus. Telemetry and rule evaluations stream directly into the terminal's console output pane, rendering diagnostic results using pure 7-bit ASCII status tokens.
- **Runner Immutability Boundary Protection:** The terminal runner harness remains protected under strict immutability rules. The AST linter and menu triggers mount via dynamic action discovery without modifying internal grid layouts, input windows, or upstream terminal primitives, keeping the local developer flight deck isolated from business logic shifts.
