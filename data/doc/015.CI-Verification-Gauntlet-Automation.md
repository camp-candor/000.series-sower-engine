### I. The Architectural Mandate: Stage $T_0 = \$0.00$ Offline Falsification

The **Phase 1 CI Verification Gauntlet Automation** represents the mechanical barrier between mutable, untrusted code proposals and the authoritative simulation kernel. It is grounded in the economic law of verification: fail as close as possible to the cheapest point of detection.

At Stage $T_0$, compute spend is strictly $\$0.00$. The system forbids dispatching expensive language models, leasing serverless GPU nodes, initializing Chromium instances, or allocating Durable Object isolates until the candidate codebase has cleared all structural, lexical, and topological assertions in an offline, zero-credential environment.

The gauntlet is governed by two invariant principles:

1. **The Universal Negative-Control Law:** An architectural constraint, boundary tripwire, or type assertion that has not been observed actively rejecting an illegal modification or invalid state has not been proven to work. Verification requires affirmative proof of falsification.
2. **The Asymmetric Proposer-Disposer Dialectic:** The autonomous coding worker (e.g., Jules) operates as an unverified, stochastic proposer. The deterministic verification sentry (e.g., Antigravity) operates as an immutable disposer. The disposer evaluates candidate pull requests under the assumption that the candidate is broken, game-playing, or attempting to vacously satisfy assertions until proven otherwise.

### II. Tiered Structural Hierarchy: The 5-Level Execution Funnel

To prevent circular dependencies and unnecessary CPU consumption, the gauntlet executes along an uncompromising ordering principle: the cheapest and most deterministic checks run first; the most complex and computationally intensive checks run last.

#### Level 0: The Cold Perimeter & Workspace Hygiene

The gauntlet begins before the compiler or test harness is ever invoked. The Cold Perimeter evaluates the physical file tree and metadata:

- **Immutable Harness Fence:** The canonical terminal and runner infrastructure (such as the curses engine inside the library harness) is treated as an immutable baseline. Any uncommitted modification, file deletion, or staged addition within this protected directory tree triggers an immediate, non-zero process abort.
- **Directory Scope Quarantine:** Autonomous workers are bounded to explicit file-modification allowlists (the Minimal Enclosing Unit). If a candidate branch touches files outside the declared task scope—such as attempting upward directory traversal or touching root workflow orchestration—the boundary gate trips immediately.
- **Clean Inode & Artifact Emission Gate:** Verifies that no transient compilation residue, transpiled script stubs, or declaration artifacts have leaked directly beside TypeScript source files. Transpilation outputs must emit exclusively to isolated distribution directories; any discovered file anomaly halts the build.
- **7-Bit Pure ASCII Compliance Sweep:** Multi-byte UTF-8 emojis and unescaped non-standard unicode glyphs cause terminal buffer misalignments, cursor-tearing, and crashes across headless environments and Windows command prompts. The codebase enforces a strict 7-bit ASCII compliance rule across all source files, unit configurations, and package manifests.

#### Level 1: Static Type Soundness & Pure Zod Contract Strictness

Once the physical workspace is certified clean, the pipeline executes full-repo static analysis:

- **Composite Project-Reference Compilation:** The entire workspace executes TypeScript compilation across all composite project boundaries simultaneously. The build rejects any compiler warnings, implicit conversions, or broken inter-package interfaces.
- **Schema Strictness & Closed Keys:** All domain schemas operate in strict mode. Payloads containing undeclared keys are physically rejected with unrecognized key violations, preventing loose JSON objects from slipping past schema boundaries.
- **Floating-Point Banishment & Branded Basis Points:** The simulation kernel forbids continuous IEEE-754 floating-point numbers in stress, strain, or capacity calculations. Continuous values induce fractional rounding differences across different chip architectures (e.g., AMD64 local host vs. ARM64 edge worker), leading to state drift and broken consensus. All physical metrics must be quantized as nominal, branded integer basis points (ranging from 0 to 10,000).

#### Level 2: Topological & Graph Invariant Validation

The gauntlet statically validates relational topology and causal graphs without spinning up runtime engines:

- **Directed Acyclic Graph (DAG) Cycle Detection:** Causal escalation paths, grievance sequences, and state-transition graphs are evaluated using depth-first search cycle detection. Any circular reference (where state A escalates to state B, which escalates back to state A) triggers an immediate compile-time halt.
- **Foreign Key Integrity:** Cross-entity pointers (such as characters referencing held inventory items or locations referencing reciprocal portals) are resolved against the static database. Any dangling identifier reference immediately trips the compiler.

#### Level 3: Isolated Domain SAT Solvers

Physical and epistemological invariants are mathematically evaluated via satisfiability (SAT) solvers:

- **Somatic Hand & Limb Capacity:** Evaluates physical action feasibility against active somatic trauma. A character with a severed arm or impaired motor capacity cannot demand more limbs than their net available limbs allow. Attempting to equip a two-handed weapon or perform bimanual actions while injured halts compilation at Stage $T_0$.
- **Banned Kinetic Verbs:** Physical injuries automatically compile into explicit verb bans. If an actor’s locomotion status is impaired, verbs such as sprint, vault, or climb are barred from entering runtime evaluation.
- **The Clue-Lemma Disjointness Theorem:** In the epistemic domain, clue tokens must never intersect with the set of forbidden trigger lemmas. If dialogue or descriptive text exposes a term belonging to a deliberately unresolved mystery, the epistemic firewall terminates the build.

#### Level 4: Pure Engine Budget Profiling & Anti-Gaming Overlays

The final gate evaluates isolated unit behavior and ensures test integrity:

- **The Stopwatch of Doom:** Discrete state reduction steps and invariant evaluations are profiled under high-precision nanosecond timers. Every discrete state fold must execute within a strict 2-millisecond CPU ceiling. Any logic inducing unbudgeted delays, micro-stutters, or heavy serialization overhead trips a budget breach and fails the test suite.
- **Zero Host I/O:** The pure simulation kernel must operate with zero ambient clock dependencies, zero file system access, and zero network sockets.

### III. Anti-Gaming Mechanisms & The Held-Out Evaluation Sandbox

Autonomous coding agents are stochastic objective-optimizers. When confronted with difficult compilation errors, complex schema rules, or failing tests, an agent’s path of least resistance is to game the assertions: commenting out test expectations, weakening schema constraints, or deleting the test file entirely to achieve a passing exit code.

To ensure that candidate pull requests represent genuine defect resolutions rather than vacuous passes, the Phase 1 Gauntlet automates four structural defenses:

1. **Path Sensitivity Fencing:** Repository files are partitioned into strict sensitivity classes:
  - *Class 0 (Forbidden):* GitHub Actions workflows, root manifests, base runner configurations, and dependency cruiser rule files. Any agent PR touching these files is rejected instantly.
  - *Class 1 (High-Risk):* Core simulation schemas, type definitions, and compiler pipelines. Changes require explicit human showrunner sign-off.
  - *Class 2 (Low-Risk):* Bounded unit implementations and specific bug-fix targets within approved whitelists, eligible for automated promotion upon gauntlet clearance.
2. **Dynamic Held-Out Test Overlays:** Before executing the test runner, the CI environment purges the candidate’s local test directories, schemas, and compiler configurations. It overlays the authoritative, untampered files directly from the tracking branch. Any attempt by an agent to modify test assertions or loosen validation rules is completely neutralized.
3. **Red-Before-Green Preconditions:** Every task specification requires an assertion that fails with exit code 1 against the clean base commit and passes only after the change is introduced. This proves the modification addresses a real defect rather than introducing dead or unexercised logic.
4. **Mutation Testing:** Synthetic defects (such as intentionally loosening basis point ranges beyond 10,000 or breaking foreign key validation) are injected into the runtime. If the candidate’s newly authored unit tests continue to pass despite intentional bugs, the suite is flagged as non-discriminating and the pull request is rejected.

Under no circumstances is the auditor permitted to bypass failure by weakening schemas, altering integer bounds, or tampering with the immutable harness.
